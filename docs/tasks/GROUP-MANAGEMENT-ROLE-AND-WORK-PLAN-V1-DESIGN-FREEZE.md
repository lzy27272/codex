本文件是本次修改的业务权威口径。冻结表示需求边界已经确定，可以据此评审实施方案；不表示代码、数据库、接口、页面或生产环境已经变化。

## 1. 本次范围

本次只冻结两组能力：

1. 增加集团董事长、集团总经理、集团副总经理三个业务角色，并增加集团总经理、集团副总经理两个岗位。
2. 为集团总经理下属的所有管理岗位增加周工作计划和月度工作计划；计划由直属主管审批，审批通过后自动形成该提交岗位的管理任务。

不在本次范围：替换既有集团CEO、让董事长承担审批、跨岗位派活、修改现有日报/工作包语义、AI自动审批、生产部署。

## 2. 角色、岗位与兼容编码

角色用于授权，岗位用于任职和汇报，二者继续分离。

| 业务身份 | 系统角色代码 | 岗位 | 默认范围 | 冻结职责 |
|---|---|---|---|---|
| 集团董事长 | `GROUP_CHAIRMAN`（新增SYSTEM角色） | 本期不新增岗位 | `TENANT`业务只读 | 查看全集团工作、计划、任务和经营视图；不配置、不审批、不派发、不执行管理动作 |
| 集团总经理 | `GROUP_GENERAL_MANAGER`（新增SYSTEM角色） | `GROUP_GENERAL_MANAGER`（新增，`GROUP_MANAGEMENT/M5`） | 集团根组织`ORG_TREE` | 集团经营管理；审批直属集团副总经理或明确直管的区域经理计划 |
| 集团副总经理 | `GROUP_VICE_PRESIDENT`（沿用既有SYSTEM角色） | `GROUP_VICE_PRESIDENT`（沿用既有岗位，`GROUP_MANAGEMENT/M4`） | 集团根组织`ORG_TREE` | 提交本人岗位计划；审批直属区域经理计划 |

兼容规则：

- 既有`GROUP_VICE_PRESIDENT`中文展示名由“集团副总”统一为“集团副总经理”，代码不变；不得同时创建`GROUP_DEPUTY_GENERAL_MANAGER`，避免双角色和历史授权分裂。
- 既有`GENERAL_MANAGER`继续表示“店总”，不得复用为集团总经理。
- 既有`ASSISTANT_GENERAL_MANAGER`继续表示“店助”，不得复用为集团副总经理。
- `GROUP_CHAIRMAN`是新增只读角色，不替代、不继承也不别名到既有`CEO`。既有CEO及其模板、投资、KPI和配置职责本期保持不变。
- `GROUP_CHAIRMAN`采用独立的账号级业务身份上下文，可以关联员工但不要求董事长岗位。选择董事长上下文时，权限严格取董事长白名单，不与账号的其他岗位或角色权限合并；因此兼任不会把写权限带入董事长视图。
- 本次不新增或重命名“区域经理”代码。现有有效区域管理任职均可进入汇报链；当前Pilot中的`OTA_OPERATION_MANAGER`兼容视为区域管理岗位之一，未来拆分独立`REGIONAL_MANAGER`需另行冻结。

## 3. 冻结组织层级

```text
集团董事长（集团业务观察层，不进入汇报和审批链）

集团总经理
└─ 集团副总经理
   └─ 区域经理
      └─ 店总
         └─ 店助 / 部门经理 / 部门主管
            └─ 一线岗位
```

审批关系不按角色名称、`level_code`或前端展示推断，唯一依据是当前有效任职的`manager_assignment_id`。

- 默认链为集团总经理→集团副总经理→区域经理。
- 组织确有直管安排时，区域经理可以显式直属集团总经理；系统不得在主管缺失时自动猜测或越级。
- 提交时冻结直属主管任职。审批时若该主管已失效，审批失败关闭；提交人撤回后按新主管重新提交。
- 任职关系必须同租户、有效期重叠、组织范围覆盖、上级为管理岗，且禁止自指和成环。
- 一人多岗按所选任职分别提交和审批，不把账号的其他岗位权限合并成审批资格。

## 4. 工作计划适用范围

“集团总经理以下”在V1中冻结为“不包含集团总经理本人”：

- 集团副总经理及其下所有获得`work-plan.submit`的管理岗位必须能够提交。
- 集团总经理只查看和审批直属下级计划，不提交本人计划。
- 集团董事长只读，不提交、不审批。
- 一线非管理岗位不得提交。

V1系统默认纳入的既有管理岗位代码固定为：

- `GROUP_VICE_PRESIDENT`。
- `OTA_OPERATION_MANAGER`（本期兼容区域管理岗位）。
- `GENERAL_MANAGER`。
- `ASSISTANT_GENERAL_MANAGER`。
- `FRONT_OFFICE_SUPERVISOR`。
- `HOUSEKEEPING_SUPERVISOR`。

新增或自定义管理岗位不得按中文名称、岗位级别或`M%`自动获得权限，必须在已发布岗位方案中显式配置工作计划权限。对已有人工编辑或门店减权方案不得由迁移静默覆盖；实施上线前必须形成差异清单并由授权管理员逐项发布，未完成的岗位不能计入验收通过。

这样可以保持董事长纯只读，并保证每一份计划都有真实、有效的直属主管审批。后续若要求集团总经理本人提交，必须先另行确定非董事长审批人并升级本冻结。

## 5. 周期和计划内容

- 每份计划只属于一个租户、一个有效任职和一个周期。
- 类型只有`WEEKLY`和`MONTHLY`。
- 周计划按租户时区的周一00:00至周日结束；月计划按自然月。保存周期起止和时区快照。
- 同一任职、计划类型、周期起始日只允许一个计划聚合；退回修改通过新修订完成，不创建第二份并行计划。
- 每项至少包含稳定项编号、标题、工作说明、优先级、计划完成时间和零至八个提醒时间。
- 提议完成时间必须晚于提交时间且位于计划周期内；最终完成时间必须晚于批准时间且仍位于计划周期内。提交时校验提议提醒晚于提交时间，批准时校验最终提醒晚于批准时间且早于最终完成时间，不允许重复。
- V1计划是提交岗位自己的工作。审批通过后，每个计划项生成一个任务并分发回该提交任职，直属主管成为任务验收人。
- V1不允许通过工作计划给其他岗位派活；跨岗位任务继续使用现有受控任务下达能力，后续需要时单独升级。

## 6. 提交、审批与修订

```text
DRAFT
  └─ SUBMIT → PENDING_APPROVAL
                    ├─ APPROVE_AND_DISPATCH → APPROVED
                    ├─ RETURN_AND_CREATE_REVISION → DRAFT
                    ├─ WITHDRAW_AND_CREATE_REVISION → DRAFT
                    └─ REJECT → REJECTED
```

- 提交时冻结计划修订、内容哈希、提交任职、直属主管任职和周期时区；提交后的修订不可原地修改。
- 主管必须逐项处理三类决定：是否同意任务内容、是否同意完成时间、是否同意提醒设置。
- 任务内容只能同意或退回，主管不得静默删除或改写；完成时间和提醒可以“同意”或“调整”，提议值与最终值都要留痕。
- 只有全部任务内容同意，且全部完成时间、提醒均形成合法最终值，才允许整单批准。
- 任一计划项不同意时整单退回，不部分批准、不创建任何任务。批准和退回请求都必须携带全部计划项的三类决定；退回至少包含一个不同意项，且每个不同意或要求调整项都必须填写原因。终止性的拒绝必须填写整单原因。
- 退回命令在同一事务内把旧修订记为`RETURNED`、复制新`DRAFT`修订，并把计划聚合状态设为`DRAFT`、当前修订指向新修订；旧修订、旧审批意见和内容哈希永久保留。
- 待审计划可以由提交人撤回。撤回命令同样原子地把旧修订记为`WITHDRAWN`、复制新`DRAFT`修订并更新计划聚合；不另建同周期计划。
- 批准后的计划修订不可编辑。后续任务调整、取消、返工和验收只走任务中心并保留时间线，不反写历史计划。

## 7. 自动形成任务

批准和任务生成是一个不可拆分的业务命令：

1. 锁定计划和待审修订，校验乐观锁版本及精确主管任职。
2. 写入审批总决定和逐项三类决定。
3. 每个计划项创建并派发一个`management_task`到`PENDING_ACK`。
4. 任务`ASSIGNEE`为提交任职，`REVIEWER`为审批任职；完成时间和提醒采用审批后的最终值。
5. 写入计划项—任务链接、审计记录和事务Outbox。

任何一步失败全部回滚，不允许出现“计划已批准但任务少建”。任务键字符串统一为`work-plan:{planId}:{revisionId}:{itemId}`，由数据库唯一约束`(tenant_id, idempotency_key)`隔离租户；重复提交或并发审批不得产生重复任务。

提醒是“到期前提示”，默认发送给任务负责人，也就是提交计划的任职；不自动提醒审批人。提醒与逾期升级不同，任务完成或取消后，尚未发送的提醒自动取消。同一提醒只允许形成一个站内通知和一个Outbox事件；外部通知通道按至少一次尝试并尽量使用供应商幂等键，网络超时下不得宣称严格只投递一次。

## 8. 权限冻结

| 权限 | 董事长 | 集团总经理 | 集团副总及以下管理岗 | 说明 |
|---|---:|---:|---:|---|
| `ui.module.work-plans` | 是 | 是 | 是 | 仅控制模块可见，不替代API授权 |
| `work-plan.read` | 否 | 否 | 是 | 查看本人任职计划 |
| `work-plan.submit` | 否 | 否 | 是 | 创建、修订、提交和撤回本人计划 |
| `work-plan.team-read` | 是（全集团只读） | 是 | 是 | 管理岗位方案静态授予；运行时仅返回直属下属 |
| `work-plan.review` | 否 | 是 | 是 | 管理岗位方案静态授予；仍须同时满足“精确直属主管”关系 |
| `task.read` / `task.review` | 仅`task.read` | 是 | 是 | 计划审批人必须能验收其作为`REVIEWER`参与的生成任务；参与人校验继续限制范围 |

冻结安全规则：

- 新增`work-record.team-read`，把团队工作“查看”与`work-record.review`“审核”拆开；董事长不得通过审核权限换取查看能力。
- 董事长只读权限白名单冻结为：`dashboard.ceo`、`dashboard.hotel`、`dashboard.operations`、`work-record.read`、`work-record.team-read`、`task.read`、`daily-report.read`、`daily-report.team-read`、`daily-operation.read`、`daily-operation.cross-hotel-read`、`operation-snapshot.read`、`operation-snapshot.compare`、`evaluation.read`、`notification.read`、`work-plan.team-read`。白名单之外默认拒绝，新增只读范围也须评审。
- 董事长导航只显示工作台、集团/区域/门店驾驶舱、团队工作、任务、日报、日运营、评价、通知和集团计划；不显示“全部功能”，并隐藏组织与权限、岗位配置、工作包配置、模板、规则配置、KPI、人事、投资、企微和系统配置入口。
- 董事长视图不得返回薪酬、奖金、个人联系方式、凭证、密钥、完整审计导出等敏感字段；集团视图优先汇总，明细按最小必要原则展示。
- 董事长不授予`*`、IAM、组织维护、岗位方案、模板维护/发布、规则维护/发布、任务创建/派发/执行/验收/取消、投资配置、KPI管理、企微管理、密钥、导出或其他写权限。
- 集团总经理和集团副总经理的业务管理权限不等于系统管理权限；本期不默认授予IAM、组织、岗位、密钥或系统配置权限。
- 审批后任务通过不暴露公网入口的`createFromApprovedWorkPlan`内部服务在原审批事务内创建，不要求审批人拥有通用`task.create`或`task.dispatch`。任务`created_by`、CREATE/DISPATCH迁移、审计和Outbox的因果操作者均记为审批账号/任职，来源快照另记`WORK_PLAN`、计划修订和审批决定，事务中不切换成平台或系统管理员身份。
- 所有可能审批计划的管理岗位方案必须静态包含`task.read`和`task.review`；任务验收仍要求当前任职恰好是该任务的有效`REVIEWER`，不得扩大为任意任务验收。
- 平台管理员可以诊断数据，但不是业务直属主管时不得代审。即使拥有通配权限，也必须通过直属主管关系校验。
- 同一岗位的计划权限来自已发布岗位方案，不随“当前有没有下属”动态增删；没有直属下属时，团队列表为空且不存在可审批计划。
- 所有表按`tenant_id`强制RLS，服务端还必须执行组织范围和任职范围校验；前端隐藏按钮不是授权。

## 9. 页面冻结

工作计划模块固定包含：

- 我的计划：周/月切换、草稿、提交、退回修订和生成任务链接。
- 待我审批：只显示提交时冻结给当前任职的待审计划。
- 下属计划：按组织范围查看历史、状态和任务完成情况。
- 集团计划：董事长的全集团只读视图，不出现任何编辑或审批按钮。

审批页逐项并列展示提议值和最终值；调整完成时间或提醒时必须明确标识并记录原因。

## 10. 验收底线

- 董事长能查看全集团业务计划和任务，但所有计划写入、审批及管理后台接口返回403，页面没有相应按钮和菜单。
- 董事长账号即使关联员工或兼任其他岗位，选择董事长上下文后仍只能获得冻结的只读白名单；其他上下文权限不得合并进来。
- 集团总经理提交计划返回403；集团副总经理及以下管理岗按任职成功提交，非管理岗返回403。
- 无主管、无效主管、自我主管、循环主管、越权主管或跨租户主管均失败关闭。
- 只有提交时冻结的有效直属主管能审批；越级领导、平台管理员或同级人员不得代审。
- 集团总经理和集团副总经理均能验收由其批准生成、且本人是`REVIEWER`的任务；不能验收未参与的任务。
- 任一任务项不同意时没有任务产生；全部同意时N项恰好产生N个任务。
- 调整前后时间完整可审计；无效、重复或晚于完成时间的提醒被拒绝。
- 同一幂等请求重试不重复建任务；并发审批只有一次成功；中途故障时审批、任务、提醒和链接全部回滚。
- 计划、任务、提醒、审计和Outbox通过跨租户、跨组织及一人多岗负向测试。

## 11. 变更控制

以下任一变化都必须先更新本冻结并重新评审：

- 董事长开始审批、写入或进入管理后台。
- 集团总经理需要提交本人计划。
- 新建副总经理代码或改变既有`GROUP_VICE_PRESIDENT`兼容策略。
- 计划开始向其他岗位派活、允许部分批准或批准后回写计划。
- 主管解析不再以有效`manager_assignment_id`为唯一依据。
- 自动任务不再与审批保持原子和幂等。
